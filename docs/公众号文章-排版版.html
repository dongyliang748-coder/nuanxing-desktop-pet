不是壁纸，不是壁纸引擎，是一个真正会盯着你光标、会提醒你喝水的桌面NPC。

起因就是一句话

我随口问了一句："能不能做个桌面宠物？"

然后它就出现在屏幕右下角了——一个戴着粉色墨镜、穿奶油白外套的Q版小人，安静地站着，偶尔呼吸时身体轻微起伏。

关键在于：它的视线会跟着你的鼠标转。

你往左上角移动光标，它的脑袋就往左上偏；你把光标停在任务栏，它就低头看你。不是简单的整体旋转，是 16 个方向各自一张的表情——每一帧都是正儿八经画出来的转头姿态。

第一次看到它真的转头看我，那种感觉挺奇妙的。

第一步不是写代码，是翻箱倒柜

做桌宠，最难的不是程序，是素材。

我早就有一套宠物精灵图，是一张 1536×2288 的雪碧图——8 列 × 11 行，每个格子 192×208，一共 73 帧。问题是它散落在某个陈年目录里，而且当时没留下任何说明文档。

所以第一步是：找到它，并且确认它是对的。

找素材花了点时间，但确认版本只花了 3 秒——当初留了一份 SHA-256 校验值：

6d47b076731878061bc80a398e743afa68b690001584410545a1ef928066a94e

复制过来重新算一遍，一致。

这一步看着多余，但很重要。当你从一堆备份里翻出同名文件时，你怎么知道哪个是最终版？哈希会告诉你。它比"我记得是这个"可靠得多。

读懂一张图：73 帧里藏着什么

雪碧图本身不带任何注释。要让它动起来，得知道每一行是什么动作。

万幸，原项目还留着一个 pet_request.json。翻开它，答案一目了然：

行 动作 帧数 干什么用
0idle6待机呼吸、眨眼
1running-right8向右移动
2running-left8向左移动
3waving4打招呼
4jumping5跳跃
5failed8失败 / 被拒绝
6waiting6等待输入
7running6处理任务中
8review6呈现结果
9look8视线 000°→157.5°
10look8视线 180°→337.5°

更妙的是，我还在项目里找到了一个当时用来导出预览 GIF 的 Python 脚本，脚本里写死了每一帧的持续时间（毫秒）：

("idle", 6, [280, 110, 110, 140, 140, 320]),
("running-right", 8, [120, 120, ...]),

也就是说，这套动画的原始节奏是有据可查的。我没有去"猜"一个看起来舒服的速度，而是直接照搬——呼吸吸得长、呼得短，眨眼快，帧间的停顿全都是设计过的。

这是复用素材最大的好处：你继承的不只是图，还有当初的审美判断。

让它浮在桌面上

技术选型上没有犹豫：Electron。透明窗口、自定义交互、HTML/CSS 做气泡和菜单，比 Python 手写 UI 舒服太多。

几个必须处理到位的点：

1. 窗口要完全透明

transparent: true,
frame: false,
hasShadow: false,
skipTaskbar: true,
alwaysOnTop: true

2. 不能挡住你干活

这点是决定体验好坏的分水岭。宠物窗口实打实占着屏幕右下角 320×400 的一块地，如果整块拦截鼠标，这一片就废了。

正确做法是按需穿透：鼠标没在宠物身上时，窗口完全透传点击，你的操作落到下面的窗口；鼠标进入宠物范围，窗口立刻接管。

win.setIgnoreMouseEvents(true, { forward: true });

划重点：这个判断放在主进程做，不要放在渲染层。

我一开始写在渲染进程里监听 mousemove，结果发现不可靠——窗口处于穿透状态时，渲染进程能不能收到事件本身就带不确定性。后来改成主进程用 getCursorScreenPoint() 每 60ms 轮询一次屏幕坐标，自己算鼠标有没有落在宠物矩形里。

这样判断权和控制权在同一个进程，不会打架。

3. 拖拽不能局限于窗口内

CSS 提供的 -webkit-app-region: drag 在窗口边缘就会失效，拖出去松手还会卡住。

真正的解法是主进程接管：按下时记录偏移量，然后每 16ms 读一次屏幕光标位置，强行把窗口钉到光标旁边。

dragTimer = setInterval(() => {
  const c = screen.getCursorScreenPoint();
  win.setPosition(c.x - offset.x, c.y - offset.y);
}, 16);

因为窗口永远跟着光标走，光标相对窗口的位置恒定不变，所以松手事件一定能收回来——不会出现"拖出去松手它就永远粘住"的经典 bug。

4. 16 方向视线

这是我最满意的部分。

素材里专门为"看"单独做了 16 张转头图（第 9、10 行），如果不做视线跟随，这两行就白瞎了。

做法是主进程轮询鼠标位置，算出宠物到光标的向量：

let deg = Math.atan2(dx, -dy) * 180 / Math.PI;
const index = Math.round(deg / 22.5) % 16;

角度从正上方 000° 起顺时针递增，每 22.5° 一档，正好映射到 16 个索引。

索引 0-7 取第 9 行的对应帧，8-15 取第 10 行。渲染层收到索引就立刻换帧，750ms 没有新的方向变化再切回待机呼吸。

结果就是：它真的像有意识那样看着你的鼠标。

打包：一个差点埋雷的细节

代码能跑不等于能交付。用户要的是"双击直开"，所以打包成了单文件便携版 exe——71MB，不装 Node、不装 Electron，扔到任何 Windows 机器上都能跑。

应用图标也不是默认 Electron 图标，而是从精灵表第一帧裁出来的暖星的脸。

npm run build   # 输出 dist/暖星-便携版.exe

然后挖到一个很隐蔽的坑，值得单独说：

便携版 exe 运行时，程序会被解压到临时目录再执行，这意味着此时的 process.execPath 指向的是临时目录里的副本，而不是你桌面上的那个 exe。

如果按常规写法拿它去写开机自启：

// 错：便携版下这个路径是临时的，重启就失效
app.setLoginItemSettings({ openAtLogin: true, path: process.execPath });

注册表里记的就是个一次性路径，重启电脑后自启静默失效，而且很难排查——因为开发时一切正常。

正确做法是读 process.env.PORTABLE_EXECUTABLE_FILE，electron-builder 会用它告诉我们便携版 exe 的本尊在哪：

const target = process.env.PORTABLE_EXECUTABLE_FILE || process.execPath;

改完之后我去注册表里核对：

HKCU\Software\Microsoft\Windows\CurrentVersion\Run
  electron.app.暖星 → F:\...\dist\暖星-便携版.exe

指向正确。

这类问题最阴的地方在于：它不报错，它只是悄悄不工作。

它现在会干什么

· 视线跟随：16 方向追着你的光标

· 拖拽：拖到哪站到哪，左右移动播放不同的奔跑动画

· 点一下：随机挥手 / 跳跃 / 举手，还会说话

· 右键菜单：摸头、喂食、陪我聊天、随手动作、提醒开关

· 定时提醒：喝水 45 分钟、久坐 1 小时、下班 18:30、晚间复盘 22:00

· 接大模型：配个 OpenAI 兼容的接口就能跟它聊天，回复显示在气泡里

整套东西跑起来占用很低，平时你不碰它，它就是在右下角安静地待着。

一点感想

这个项目从"随便问问"到落地，真正难的地方全都不在 AI 帮我写了多少行代码，而在这些地方：

· 素材找到了，怎么确认是正品（哈希）

· 动画怎么动才对（找回原始帧时长）

· 鼠标为什么放不透、拖不动（穿透和拖拽的控制权归属）

· 明明写了开机自启，为什么重启后没反应（便携版的路径陷阱）

前两个靠"查证而不是猜"，后两个靠动手实测。

AI 最大的价值，是把"写代码"这件事的成本压到几乎为零，让你能把精力全部砸在验证和判断上。

而最后决定这东西好不好的，恰恰是那些它没法替你猜的部分。

项目已开源，里面有一键启动脚本、完整的配置说明和打包命令，拿去改造成你自己的宠物也很方便：

https://github.com/dongyliang748-coder/nuanxing-desktop-pet
